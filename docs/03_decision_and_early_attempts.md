# 03 · 决定：不训练解说模型，把“什么时候说”和“说什么”拆开 —— 以及框架定型前的两段尝试

> **一句话**：五个出发点推出同一个决定 —— **先做一个读画面的模型把仪表盘读成数；“什么时候说”交给规则；“说什么”交给模型；说完由代码核对**。定型前走过两段路：第一段把整棵决策树塞进提示词、让千问自己挑，结果说不出一个具体的数；第二段先找底座、跑通“记录员 + 说话人”两层，暴露出三个问题，直接决定了中间要加一层“编导”。

---

## 1. 为什么这么决定：五个出发点

| 出发点 | 从哪来 | 推出什么 |
|---|---|---|
| 隔固定间隔问模型，必然慢半拍 | Video2Text 的“念完再问”，我试的 2 / 4 / 6 秒（[02 §6](02_video2text_and_qwen.md#6-最重要的发现隔固定间隔问模型必然有损失)） | “什么时候说”不能靠定时问，要靠事件触发 |
| 判断解说好不好，看的是关键事件有没有被及时、正确地说到 | 我给千问实验定的评估方法 | 何不直接拿关键事件当开口的依据 |
| 它学会了何时说，但说不到点上，说的也不一定最紧急 | 看千问的解说 | 要约束它：在特定的时候说最必要的话 |
| 它经常看错、出幻觉 | 编出 72 / 42 / 40 号玩家 | 要先让它把画面看明白 |
| 每次跑都不一样，提示词也挡不住 | 只改提示词，沉默率从 15% 跳到 98% | 要用规则：可控、可复现 |

**决定**：

- **第一件事：先做一个读画面的模型** —— 用 OCR 式的识别把仪表盘上的数字和图标读出来，让“看明白”有可靠的事实
- **“什么时候说”交给规则**：事件由读数推出来，出现就触发，按急缓排队或打断，不再隔一段时间问模型
- **“说什么”交给模型**：模型只把选定的那一件事说成一句人话，说完由代码核对
- **不训练解说 / 决策模型**：通用模型不训练就看得懂大意，缺的是约束和可靠的事实。（后来训练的只有读仪表盘的感知模型，那是另一回事，见 [06](06_hud_perception.md)）

> [!IMPORTANT]
> **规则不只是因为延迟低，更是因为可控、可复现**：只要画面读对了、规则写对了，不管跑多少次，都一定会路由到我想让它说的那条提示上。每次说什么是确定的，只是措辞不一样。

## 2. 第一段尝试：把整棵决策树塞进提示词（08-27 → 08-28）

**是什么**：同一时期，同事整理过一份对局决策框架（按局势 / 资源与状态 / 走位 / 交战四块，列出老手该问自己的几十个问题，原件不公开）。最直接的做法：整棵树逐字写进提示词，让千问每看一段录屏，从所有分支里挑出最相关的至多 3 个，定一个最重要的，写明它命中哪一条决策项，只针对这条说一句建议；答不上来就换分支，或者不说。提示词里只有问题清单，没有游戏知识。

**看什么**：它挑哪些分支、不挑哪些，说出口的话里有没有具体的数，以及它看到的和同一时刻的仪表盘读数对不对得上。

<details>
<summary>一次请求里实际喂了什么、它输出什么</summary>

- **切段**：录屏切成固定时长的小段（720p）按视频喂；最近 3 段带视频，更早的段只留一行文字摘要（把以前的 JSON 原文回灌会诱发逐字复读，只作对照）
- **段长**：17 次运行里 13 次是 6 秒一段，另有 2 秒、4 秒对照。2 秒时单段延迟（约 3 秒）和配音（2–3.4 秒）都超过段长，出口排队；6 秒稳但有 10 秒以上的尖峰；4 秒两者都放得下
- **模型**：千问 Omni（未微调），temperature 0，只要文字
- **token**（6 秒一段）：第 1 段 prompt 5,677（视频 3,566、文字 2,067、音频 44）；窗口攒满 3 段后 prompt 13,090
- **提示词只有一个出处**：从决策框架 md 渲染，代码里不许手写分支名。改提示词时踩过：给过句式样例，样例被原样抄进建议，只好回退成只描述不举例；NONE 示例 JSON 里用中文顿号当分隔符，示例本身不合法，模型就跟着输出不合法的 JSON；“不要重复”写了三遍仍压不住，最后交给代码去重
- **输出**：每段一个 JSON —— 感知四格（敌情 / 周边风险 / 对局进程 / 队友状况）每段必填；`skills` 最多 3 条，每条带分支路径、逐字取自框架的决策项、0–1 的置信度；再定一个 `primary_skill` 和一句 `advice`

```json
{"situation": {"敌情": "远处树后有人，刚被击倒", "周边风险": "空投箱位置未侦察", "对局进程": "剩约40人", "队友状况": "无队友"},
 "event": "精准击倒一名敌人",
 "skills": [{"name": "交战/信息共享", "decision_item": "（框架里“要不要把敌人位置报给队友”那一条）", "confidence": 0.9}],
 "primary_skill": "交战/信息共享", "advice_type": "提醒", "advice": "赶紧标记敌人位置，告诉队友。"}
```

这是一局单排的第 2 段输出（分支名和决策项换成了我的转述）：它写“无队友”（对），建议却让你“告诉队友”—— 同一条 JSON 自相矛盾。
</details>

### 结果：说不出具体的数

17 次运行共给出 76 条建议（28 条夸赞、48 条提醒 / 行动），**带数字的只有 2 条**：“只剩5人了，小心别被偷。”“只剩7人了，注意听枪声别暴露。” —— 都是屏幕左上角最大的那个剩余人数。教练该报的数（血量多少、弹匣还剩几发、离缩圈还有几秒）**一条都没有**，这些数就在同一个画面的仪表盘上。

同一局（单排）同一时刻的人审读数，和它说过的原话：

| 录像时间 | 这时仪表盘上的数（人审） | 它说的 |
|---|---|---|
| 8:52–8:58 | 剩 39 人，弹匣 41 发；缩圈倒计时 2:27 | “别贪 loot，赶紧跑毒。” |
| 9:46–9:52 | **血量 41%**，正在打急救包；弹匣 34 发；剩 19 人；缩圈倒计时 0:51 | “贴着墙边打药，别露太多身子。”<br>“边打边看墙后，别给对面扶人的机会。” |
| 9:52–10:00 | 血量回到 75%；缩圈倒计时 0:39 → 0:27 | “别直走，贴着草坡慢慢挪过去。”<br>“注意草丛，别被发现了。” |

### 它不选的分支，正好是要读数的

除去夸赞，48 条主建议按分支数：**问自身状态的那一支（子弹、头盔护甲、血量）一次没被选中**，**问毒圈的那一支也没当过主建议** —— 175 段里从没说过圈在哪个方向、离圈多远。它答不上来，分三层再加一条：

- **读不出（像素太小）**：血条只有 4 像素高、护甲耐久条 10×4 像素。后来用 Qwen3-VL-8B 零样本专门测过（每个框裁出来单独问）：血量 0.01、护甲 / 头盔耐久 0.07、背包物资 0.03。这次喂的是 720p 整帧视频，只会更难【推断：没有直接测过千问 Omni 读血条】
- **看不懂（要懂游戏才看得明白）**：右上角小地图。圈外时有一条白色虚线指向安全区，要知道规则才读得出意思；后来框架里的说话人还编出过“往西北跑”，裁出小地图一看，虚线四次都指向南
- **读得出，但不会用**：缩圈倒计时、离圈距离是大数字，裁出来单独问读得出（倒计时 0.98、距离 0.88）；可提示词没说这些数该怎么用，它一次也没报过
- **没有知识**：框架是一张问题清单，不是答案。“血量”只是一个要回答的问题；血量多少该打药、打哪种药、圈外急救包还管不管用，提示词里一个字都没有

大的读得出：它在感知里写的剩余人数，和读数比 168 次对了 161 次（差 2 人以内）；错的 7 次里有 6 次写的是“剩约20人” —— 正好是提示词 JSON 示例里的值，**看不清就照抄示例**。

- **赢了还当实况在夸**：赢了之后连说三遍“这波火封得漂亮！” —— 结算页 / 回放认不出来
- 219 条建议里 63% 含“别”，几乎全是禁止式；13 条夸赞全是夸枪法（夸赞靠 event 触发，而 event 只认得出有击杀横幅的事）
- 样本小、单次跑，同片段两次跑分支一致率只有 4/14，当方向看

### 往下走的两条路

要补上“没有知识”，最直接的是把知识交给模型，让它自己判断；另一条是先在模型外面判断好，只把这件事用得上的那一条知识给它。

| 做法 | 能不能答对 | 延迟 | 依据 |
|---|---|---|---|
| 这一步：问题清单给模型，它自己挑 | 细处读不出、小地图看不懂、没有知识，答不准 | 6 秒一段平均 3–5.5 秒、尖峰 8–13 秒（没开思考） | 实测 |
| 把整本知识库也写进提示词 | 知识在了，但每次还得自己从一大段里找对那一条 | 每次请求都要多读一大段文字 | 没试过 |
| 做成 Agent：遇到情况再去查知识库 | 看它查得准不准 | 查一次就多一轮模型调用，而一轮就要 3–5 秒 | 没试过 |
| 让它先想清楚再说（开思考） | 可能更准 | 输出变长：另一个任务上开思考一次输出 3,164 个 token，关掉只有 23 个 | 另一个任务上的实测 |
| **后来的做法：规则拿读数先判断，只把这件事的那条知识交给说话人** | 判断在代码里，能核对、能复现 | 判断不调模型；说话人连语音约 1.1 秒 | 实测 |

> [!IMPORTANT]
> 让模型自己判断，有两个毛病 —— **不见得对**，而且**慢**；想让它判断得对，就得多给知识、让它多想，结果**更慢**。在这条路上，对和快互相拖累。规则把“判断”从模型里拿出来先做完，说话人手里只剩这件事和这一条知识，不用再想，于是对和快可以同时拿到。

**这一步留下的**：每句话都要挂在决策树的某一条上，挂不上就不说。**这一步暴露的**：一次大模型调用同时做“看画面 + 挑分支 + 措辞”，细处读不出、手里没有知识；重复、过时这类跨时间的约束，写进提示词管不住。**所以下一步**：细处的数不再指望大模型顺带看出来，先把仪表盘读成一帧一行的数；再由规则拿数去对决策树、配好那一条知识，模型只负责把选定的那一件事说出来。

## 3. 第二段尝试：先找底座，跑通“记录员 + 说话人”（08-31 → 09-01）

**为什么做这一步**：第一段把“何时说、说什么”全交给一次模型调用，管不住。这一步先把“何时开口”从模型里拿出来。先要一个**能持续收画面、能打断**的底座：

- **Google 的 agent 框架（ADK）**：官方例子原样跑通，模型和工具调用都没问题 —— 放弃不是因为调不动。把设想套上去实测：每段 4 秒的画面仍要同步问一轮模型，一轮 10.3–16.5 秒，等回答时收不到帧，后面十几段直接“无帧，跳过”；原版也要先塞一句 Hello 才开始干活。**说到底还是“来一次请求、答一次”的形态**，做不到持续看画面、没事不说、有事自己开口。值得借的是“主动插话”这个控制思想，为它继承整套不划算。
- **从 vLLM-Omni 里抽运行时**：它现成有“画面 → 过滤 → 缓冲 → 触发 → 打断”这条链，但“新帧来了自动开一轮”默认是关的，只有客户端发提问才答一轮 —— 这正是要自己补的那一格。当时 vllm-omni 新版本线对齐 vLLM 0.24，而 H20 的驱动把 vLLM 卡在 0.19.1，装不上，所以**抽了 4 个文件出来**（[`runtime/`](../runtime/)，Apache-2.0，来源见 `runtime/ATTRIBUTION.md`），自己填触发和提示词。打断 = 发一个软中断信号 + 取消正在生成的任务。

**09-01 两层跑通**：

- **记录员**决定什么时候开口：每帧先用像素亮度判断击杀横幅出没出现（6 毫秒），亮了才让本地 8B 模型读横幅（460 token / 0.27 秒），按“动作 + 玩家号”去重后触发
- **说话人**决定说什么：触发时拿最近一段画面（每帧标上时间），说一句话

**跑通后暴露三个问题**：

1. **模型正在说话时来的事，被悄悄丢掉**：检出 4 次击杀，只开口 3 次
2. **说的话重复**：三次开口只隔 2–3 秒，看到的画面大量重叠，说得几乎一样
3. **只认击杀横幅一种事**：仪表盘 19 个框只接了 1 个；每加一类事都要配闸门、读取器、去重规则，没有抽象

当时笔记里已经写下了答案的方向：“**最急的打断、次急的排队、不急的丢掉并记账**”，以及“**重复应该在触发层就避免，而不是等模型说完再压**”。这三个问题直接决定了下一步：在记录员和说话人中间加一层编导 → [04 · 三层教练框架](04_coach_framework.md)。
